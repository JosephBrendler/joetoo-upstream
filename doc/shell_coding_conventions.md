# shell coding conventions

script_header_joetoo contains hundreds of variables and functions for scripts that source it.  It must support a variety of needs including running in the init script in joetoo custom initramfs (i.e. in a busybox/ash shell). For this reason, I have determined that script_header_joetoo must be as close to 100% POSIX compliant as possible, and I have audited that requirement with AI assistance several times.

Most of the scripts maintained in the joetoo-sources repository are designed to run in a modern Bash shell in a current stable Gentoo (joetoo) system.

## Guidelines for POSIX script development (things that will go into script_header_joetoo)
All POSIX shell variables are inherently global in scope. When applying localization principles:
* in POSIX shell scripts, any variable used by a function as the argument providing exit status must be initialized to 0 at the beginning of that function and must not be unset by that function. To reduce the risk of functions over-writing each other's return values, all functions must use a uniquely named variable to return an exit status, and this variable should be 'localized' by prefixing that identifies the function but does NOT include a leading underscore '_' character. This will differentiate them from localized variables which must be unset before the function exits.
* any variables used only locally in a function must be namespaced with a variable name prefix identifying the function (including a leading underscore '_' character), and all such variables must be unset at the bottom of the function. A variable cannot be in both of the above categories. (3) A third category, consistent with the first sentence above is external (global) variables - these must be neither 'initialized' by the function, though the function may logically 'modify' them, and they must NOT be unset by the function.

## Guidelines for Bash AND POSIX script development for joetoo
* In BASH and POSIX scripts, I create and use a "pseudo-boolean" data type by defining TRUE=0; and FALSE=; at the top of my globally sourced header file (script_header_joetoo).
* I typically use all capital letters to name these, but in POSIX functions, I "localize" the name with a lowercase prefix.
* These variables are only ever assigned "=$TRUE" or "=$FALSE", so they can be reliably tested like this: ```"VAR=$TRUE; [ $VAR ]"``` --> will always evaluate success and ```"VAR=$FALSE; [ $VAR ]"``` --> will always evaluate fail. so ```"if [ $VAR ]; then" or "while [ $VAR ]; do"``` are also reliable constructs.

## Bash script variable management
Bash scripts should apply the following rules for variable management:
* variables used only in the function must be initialized at the top of the function with the "local" keyword, and they should be "namespaced" by prefixing the descriptive variable name in a way that identifies the function and begins with an underscore character.
* global variables should not be prefixed in this way, so they are visibly differentiated from local variables, since that would be unnecessary for variables initialized with the local keyword in bash scripts
* bash scripts need not follow the "unsetting" convention for described for POSIX scripts, above.

## script_header_joetoo architecture (context for scripts that will source it)
### Three Pillars: FUNCTIONAL SYSTEMS + UI & Layout Management:
* Unicode rendering and measurement, Grapheme width, smart_wrap_n, pad, DEC Boxes, Cursor Control, unicode boxes, sh_countdown, progress bar...
* Messaging & Severity Tier: j_msg, emit, verbosity levels, debug logic, environment-sensitive integrated messaging and logging (verbosity, QUIET, DEBUG, INTERACTVE, LOGGING, EMOJI_CAPABLE...)
* CLI Framework: (app_configure, validate_status-file, initialize_vars, display_vars, show_config, run_sequence, process_cmdline and usage (both easily locally-extensible for new apps) plus app templates for both simple and complex interactive sequences).
### "Core" of script_header_joetoo architecture:
* (Validation, Logic Layer) containing Cross-Cutting Utilities such as isnumeric, isint, ishexint, checkroot, checkboot, and vercomp. These utilities are used by all pillars and do not belong to a specific one.
### Foundation:
* Initialization and run-once up-front work, where global variable definitions live.
